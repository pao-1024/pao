# 硬件开发平台规划

项目以 PAO 验证 Agent 时代的硬件开发新流程：将电路、固件、运行环境和机械结构纳入 Agent 可操作的工程，以评估结果驱动修复。电子工程部分从真实模块的引脚、供电约束、驱动、仿真模型和安装封装出发，生成相互对应的软硬件工程；机械部分正在 Blender 中开展 Agent 驱动的建模与刚体动力学评估研发。PAO Studio 是将这些工程路径发展为产品化工作台的方向，全流程 Skill 是后续复用方式。

核心价值是在没有实物模块、或者尚未打板时，先开展设计、检查和固件开发。已有模型覆盖的接线与业务问题可以提前发现；需要真实电气环境的结论，再通过样板与实物测量确认。

## 已实现的实验能力

工作台实验原型位于 [experimental/platform](../experimental/platform/README.md)，目前在本地运行。

- 真实模块组合：使用有官方资料和明确型号的 ESP32-S3、显示、音频、电机驱动及温度、光照、温湿度传感器，展示真实引脚，支持传感器多实例与地址分配。
- 设计检查：自动补齐供电、公共地、复位、使能和匹配负载，检查电压、电流预算、GPIO、总线角色与地址冲突。
- PCB 工程：按指定模块的真实安装封装生成双层模块安装板，检查占位、铜连接、净距、钻孔和阻焊规则，通过后导出 Gerber、钻孔、BOM 和装配资料。
- 固件与软件在环：按当前接线生成固件，使用 ESP-IDF 编译并在 esp32sim 中执行，观察 UART、OLED、I²S、电机桥臂和传感器寄存器行为。
- Agent 开发：从自然语言选择内置模块、接线、生成 PCB 和业务程序，执行编译与仿真验收，把实际错误反馈给模型进行有上限的修复。

这些能力已在有限的器件目录和接口模型中实现。模块安装板不等于重新设计模块内部电路；软件在环不验证温升、射频、声学、机械负载或传感器实际精度。PAO 参考模拟器的位姿按两轮 PWM 与简化运动关系计算，与 Blender 中的刚体仿真研发分别维护。当前没有云端项目保存、团队协作服务或付费套餐。

## 当前研发：机械结构与刚体仿真评估

机械结构包括外壳、底盘、支架及其装配。自动化设计与仿真正在 Blender 中开展，由 Agent 驱动建模和仿真，结构模型是 Agent 操作的工程对象，刚体动力学仿真承担机械行为的评估环节。

评估需区分几何 / 装配与动力学：前者检查尺寸、接口、孔位和干涉，后者回答轨迹是否符合预期、接触是否合理、姿态是否稳定。几何、装配、质量、惯量和关节等参数需与场景一起核对；具体观测方式、阈值和通过条件按工程定义，不预设已有统一指标或已通过验收。刚体动力学不用于证明外壳强度、形变或散热性能。

研发验证应保留可复现的工程、场景参数与仿真结果，并以固定条件检查修改前后的行为。与电子工程的工具对接、统一验收及实物对照仍需按阶段验证；刚体仿真结果不代表实机交付已完成。

## PAO 验证什么

PAO 把语音、显示、音频、底盘和执行机构放到同一台设备中，验证模块化描述、驱动接口、固件运行、模拟器观测与实物接线之间是否一致。PAO 参考机与工作台的自由组合板型分别管理，各自使用匹配的模块和驱动，不将不同型号视为可直接互换。

后续产品验证需要对照同一份设计记录软件检查结果、打板或组装发现的问题，以及实际运行结果。平台优先吸收能够复用的模块定义、接口约束和验收场景。PAO 的单机功能通过，只能证明对应设计与场景，不能作为所有硬件组合的正确性证明。

## 产品推进方向（规划中）

### 从器件目录到可复用工程

扩展真实模块、驱动和接口，提供可复用的设备方案。新增模块需要同时具备可核对的针序与供电要求、对应驱动、仿真行为、机械封装和验收场景，才能进入自动选型。

阶段完成的判断是：新项目能使用这些模块完成选型、接线检查、固件编译、仿真及工程导出；遇到不支持的型号或资源冲突时，能够指出具体原因。

### 将工程路径整合为 PAO Studio

以本地实验原型为起点，将电路、固件、仿真与机械研发工具整合为可复用工作台。统一工程身份、工具输入输出和结果记录，让不同环节能围绕同一设计交接。

阶段完成的判断是：同一设计能恢复对应的代码、结构、构建产物与评估记录；各环节状态和失败原因可追踪，未完成的集成与验收明确显示。现有实验代码作为产品化基础，不等同于成熟工作台已交付。

### 把完整流程封装为 Skill

将电路、固件和结构生成，以及构建、仿真、评估、错误反馈与修复编排为 Agent 可复用的 Skill。固化工具的输入输出约定、工程产物、验收步骤、失败信息和修复终止条件，使同一流程能够用于不同需求。

阶段完成的判断是：Agent 能从明确的需求与验收条件启动流程，保留各阶段产物与证据，并在不支持的模块、约束冲突或修复预算耗尽时停止并报告原因。Skill 的目标是自动完成工程与仿真验收；未经实物验证的结果不作为实机交付完成的依据。

### 从单次仿真到团队回归

支持工程保存、版本比较、团队审查和批量软件在环回归。把硬件与固件修改纳入同一份可审查的工程，持续记录检查与场景执行结果。

阶段完成的判断是：同一工程能被其他成员恢复和执行；引脚、驱动或业务变化后，可以重复运行既有场景并定位失败，而不是依赖一次手工演示。

### 从软件检查到实物对照

增加硬件在环、样板装配与实物测量，把模型输出与实际数字接口、负载及业务行为对照。再根据器件和板卡的实测结果修正模型、约束和验收条件。

阶段完成的判断是：同一份工程能够对应明确的物料版本、制造文件、固件产物、仿真记录和实物验收记录。未经实测的模拟量与物理性能不能标记为已验证。

## 商业化假设与验证

首批目标用户是独立开发者和小型硬件团队，优先观察两类任务：实物尚未齐备时的原型开发，以及打板前的设计检查。这些是待验证的用户与场景假设，付费意愿和节省成本需要通过实际项目确认。

可能的付费服务需要分别验证：

- 团队工程服务：项目保存、版本审查、共享模块和验收记录。观察团队是否持续用平台交接与复用工程。
- 托管编译与仿真：提供可重复的构建环境和批量场景执行。观察本地环境维护及回归执行是否构成实际负担，并核算算力与模型调用成本。
- 私有模块库与工程支持：接入团队自有器件、驱动、模型和封装，协助输出可复核的工程资料。观察用户是否愿意为器件接入、设计检查及交付支持付费，并核算维护成本。

定价、计费方式与交付责任需通过真实项目和付费试点确认。早期应记录首次运行所需时间、软件阶段发现的问题、实际打板与组装返工、工程复用情况及服务成本，用这些证据判断产品价值，不预设节省比例或把仿真通过当作硬件质量承诺。
