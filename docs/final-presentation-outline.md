# PAO 决赛答辩大纲

面向 2026 1024 Hackathon 智能硬件赛道，按 10 分钟、十五页展示设计：讲述约 9 分 15 秒，预留约 45 秒给切换和现场停顿。视频按讲述需要选择片段，时间安排不要求将全部视频完整播放。核心叙事是：**探索 Agent 时代的硬件开发新范式：代码让 Agent 能动手，评估函数让 Agent 知道是否做对，模拟器让评估可自动执行。**

可运行的演示稿见根目录 [presentation/](../presentation/README.md)。

观众应记住三件事：硬件研发包含电路、嵌入式软件、机械结构三类核心设计，我们尝试让 Agent 参与全流程；仿真、测试与评估贯穿三者，帮助确定下一步修改；代码、工具执行和反馈共同缩短开发迭代。电路与嵌入式软件展示现有代码及透明芯片级仿真，机械部分展示当前在 Blender 中开展的 Agent 建模与刚体动力学评估研发。PAO 实机演示之后，再展望 PAO Studio 平台化与全流程 Skill。

讲述顺序是先用“万物皆代码，驱动全流程 Agent 自动化”总览三类核心设计，再说明如何把软件工程已有的版本管理与 PR 协作方式延伸到硬件工程。随后解释贯穿设计的评估函数，电路部分分别展示真实 TSX 与图纸局部、接线单元测试、生成的全图与结构化产物，再展开嵌入式软件的运行评估和机械结构。ESP-IDF 构建作为运行页的固件输入简述，芯片仿真是自动评估的关键能力。各环节由 Agent 操作、工具执行，并以评估反馈驱动修复；区分已有实验实现与当前研发状态，不把全流程方向表述成完整整机已全自动验收。

## 讲述口径

开场可说：“硬件研发可以概括为电路、嵌入式软件和机械结构三类核心设计。我们正在探索让 Agent 参与这三类设计的全流程，并用仿真、测试与评估判断结果。代码让它能动手，评估函数让它知道是否做对。我们用 PAO 验证这条路径，再探索如何复用到更多项目。”

收尾可说：“当前，PAO 是我们对这套硬件开发流程的实验性验证。下一步，我们会继续打磨工具接口、评估规则与失败修复，让设计、构建、仿真和评估衔接得更稳定。未来，再把这套工作流封装为可复用的 Skill，让 Agent 将验证过的方法带到更多硬件项目。”

“评估函数”是可执行的规则和断言：先明确完成条件，再把工程或运行结果与条件比较，返回通过或具体错误。首份有效验收场景由模型提出，并在修复中固定；仍需核对场景是否充分表达人的需求。固定标准能约束修复过程，不意味着已经完整证明需求正确。

硬件工程资产入库，是把软件工程已有的版本管理能力用于电路、固件、模型和验收规则，让团队能查看设计变更、复用模块，并依据锁定版本重新构建。当前可追踪资产包括 TSX 电路、固件源码、Rust 模型、测试和构建配置；`tmp/studio/` 中的生成工程不会自动进入 Git，需整理源码、配置与验收材料后保存入库。Blender 资产可采用同一流程，二进制模型应附预览和变更说明，较大的构建产物关联明确工程版本；当前仓库没有 `.blend` 文件。

硬件变更进入 PR 后，接线、固件驱动、图纸与验证结果可以共同审查。示例展示 `Controller.tsx` 新增 Trig / Echo 接线，说明软件协作方式如何支持跨电路与固件的修改。相关 CI 按路径触发：Hardware 检查连通性与重新生成的图纸一致性；Firmware PR 只做静态检查，完整 ESP-IDF 构建在 `main`；Simulator / Platform 做检查、单测与构建，不执行真实应用 SIL。Blender 仿真及实机验收需另附证据。工作流配置说明现有自动检查范围，不表示已配置强制合并门禁。

电路代码页摘录真实 `Display.tsx` 的 `OledModule`，保留 SDA、SCL、VCC 和 GND 的网络表达式，显式注明省略布局属性。单元测试页将现有表驱动测试中的 OLED 条目等价展开为 GPIO41 / SDA、GPIO42 / SCL 两条断言；预期接线独立记录，不从电路源码导入。`assertNetwork` 比对 Circuit JSON 中网络的全部成员，缺线或额外短接都会失败，断言给出实际与预期差异。图纸页集中说明 SVG 供人审查、Circuit JSON 供工具检查。

PAO 参考接线测试与本地实验的电气、PCB 检查分别说明。后者由 `connectionError`、`electricalReport` 和 `manufacturingDrc` 检查短接、电气约束与制造规则；短接检查依据网络关系和铜几何，不计算模拟短路电流。生成图纸或单元测试通过不能代替 PCB 和实物验收。

正式固件由 ESP-IDF 编译、链接后进入芯片仿真；构建成功只说明生成了固件，业务是否正确仍需运行验证。自由组合应用的运行评估用 `verifyApplication` 核对 UART 状态、实际 I²S PCM 峰值与音调频率、电机桥臂占空比及暂停归零；OLED 当前检查显存是否到达，不逐像素判断画面。PCM 峰值 ±50、音调 ±25 Hz、占空比 ±1 个百分点是当前实现中的验收容差，不是传感器、电机或实机测量精度；数字波形测量也不等同于真实声学表现。

“全自动”指已支持模块范围内的选型、工程生成、编译、仿真验收和有限轮次修复；需求与验收目标仍需人确认，平台不自动刷写实物或下单生产。根目录 `hardware/` 的 TSX 是 PAO 参考接线图；Studio 生成的是模块安装载板，不表示重新设计了采购模块的内部电路。

“对固件透明”指正式应用与驱动沿用原有执行路径，不需要模拟器专用业务分支。主要固件链路可以无实物运行，覆盖范围取决于已有芯片和外设模型，当前没有“绝大部分代码”的覆盖率统计。软件在环不验证温升、射频、声学、机械负载或传感器实际精度。

机械结构包括外壳、底盘、支架及其装配。自动化设计与仿真是当前研发工作，由 Agent 驱动 Blender 建模；几何与装配检查评估尺寸、接口和干涉，刚体动力学仿真评估运动、接触和姿态。具体观测、阈值及通过记录按实际场景确认，不把评价问题写成已落地指标。刚体仿真不能据此证明外壳强度、形变或散热性能。PAO 参考模拟器的 PWM 简化位姿与 Blender 刚体仿真是不同实现，机械仿真结果也不代表实机已通过验收。

PAO Studio 放在实机演示后的未来展望中，表达将工程路径平台化、产品化的方向。仓库已有本地实验原型与部分自动开发机制，这些代码是能力证据，不代表成熟工作台已经交付。PAO 参考机和实验原型的自由组合板型分别维护；实车演示不能证明任意组合通过实物验收，也不能据此宣称 PAO 整车由 Studio 一键生成。后续推进目标见[平台规划](platform-roadmap.md)。
